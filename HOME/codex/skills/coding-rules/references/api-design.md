## API設計のルール(REST)

### リソース指向のURI設計

動詞ではなく名詞(複数形)でリソースを表現し、操作はHTTPメソッドに委ねる。

```
# BAD
POST /createUser
GET  /getUserById?id=1

# GOOD
POST /users
GET  /users/1
```

### ステータスコードを意味に応じて使い分ける

- `200`: 成功(GET/PUT/PATCH)
- `201`: 作成成功(POST)。可能なら`Location`ヘッダーを付与する
- `204`: 成功・レスポンスボディなし(DELETE)
- `400`: リクエスト不正(バリデーションエラー)
- `401`/`403`: 未認証/認可なし
- `404`: リソースが存在しない
- `422`: 型は正しいが値がセマンティックに不正

### エラーレスポンスの形式をプロジェクト内で統一する

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "email は必須です",
    "details": []
  }
}
```

### 一覧取得はページネーションを前提にする

無制限にレコードを返すエンドポイントを作らない。カーソルベースまたはlimit/offsetのいずれかに統一する。

### 破壊的変更はバージョニングで吸収する

既存クライアントに影響する変更(フィールド削除・型変更等)は、新バージョンのエンドポイントを用意するか、後方互換を保つ形で追加する。

### 外部キー参照は必ずテナントスコープを検証する(IDOR対策)

ユーザー入力から外部キー(他レコードのID、例: `manager_id`/`department_id`)を受け取って紐付ける場合、その参照先が操作ユーザーと同一組織/同一テナントに属するかをrepository層で検証する。検証を怠ると他組織のレコードを不正に紐付けられる。新規エンドポイントを追加したら、認可漏れが無いことの確認に加え、他組織/他テナントのデータが結果に混入しないことを検証する回帰テストを必ず追加する。

### フロントエンドとバックエンドで判定基準を一致させる

同じ概念(祝日・休日・権限など)を判定するロジックがフロントエンドとバックエンドの両方に存在する場合、参照するデータソースが完全に一致しているか確認する。外部API由来のデータとDB由来のデータを安易にORで合成すると、UIの表示と実際のサーバー側判定が食い違う実害バグになりうる。

同じ閾値を複数箇所で判定する場合は、比較演算子の境界(以上`>=`か超過`>`か)も一致させる。片方だけ境界を含む判定にすると、閾値ちょうどの値でフロントとバックエンドの結果が食い違う。

### 外部入力の値域を明示的に制約する

クエリパラメータやリクエストボディの数値(日数・件数等)に、業務上妥当な範囲を明示せず、型さえ合えば何でも受け付けてしまうエンドポイントを作らない。妥当な最小値・最大値が決まっているなら、`Field(ge=..., le=...)`や`Query(ge=..., le=...)`等のバリデーション層で制約する。

### CSV出力はインジェクション対策を行う

CSVに出力する値(氏名・部門名など、ユーザー入力に由来しうる文字列)をそのまま書き込むと、値が`=`/`+`/`-`/`@`で始まる場合に表計算ソフト(Excel等)で開いた際に数式として実行される「CSVインジェクション」のリスクがある。出力前に、先頭がこれらの文字なら無害化する(先頭にシングルクォートを付与する等)共通ユーティリティを用意する。
