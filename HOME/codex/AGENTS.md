# グローバル設定について

このファイルは プロジェクトを問わず全セッションで読み込まれる。
プロジェクト固有の事項は各リポジトリの `CLAUDE.md` に書き、ここには環境・作業環境・全般的な振る舞いなど横断的な内容のみを記載する。

## 実装ルールの適用

以下のルールはコードを実装・変更する場合に適用する。パスが指定されているルールは、該当するファイルを変更する場合にのみ適用する。
リポジトリ内の `AGENTS.md` や `CLAUDE.md` にプロジェクト固有の規約がある場合は、その規約を優先する。

### Claudeから承認済みプラン付きで実装を移譲された場合

プロンプトで承認済みのプランファイルを指定された場合は、次のルールを適用する。

#### 着手前

- 指定されたプランファイルを最初に全文読む。
- 対象リポジトリの `AGENTS.md`、`CLAUDE.md`、README、設定ファイルから、実装規約と検証コマンドを確認する。
- 現在のブランチ、作業ツリーの状態、既存の未コミット変更を確認し、ユーザーや他のエージェントの変更を保持する。
- プランは承認済みの実装範囲として扱い、再設計やプランレビューをやり直さない。

#### 実装中

- プランに記載された変更だけを実装し、無関係なリファクタリングや機能追加を行わない。
- 命名や局所的な実装方法など、プランの方針を変えない詳細は合理的に判断して進める。
- プランとリポジトリの現状が食い違う場合は、コードと履歴を調べて原因を確認する。
- プランにない大きな方針転換、公開APIやデータモデルの変更、破壊的操作が必要な場合は、その変更に着手せず停止して理由を報告する。
- 安全に分離できない未完成の実装を残さない。ブロックされた場合は、整合性を保てる地点までで作業を止める。

#### 検証

- 変更箇所に近いテストから実行し、その後にプロジェクトで定義された関連テスト、lint、型チェックを実行する。
- 失敗した検証を隠したり、検証を通すために無関係なコードを変更したりしない。
- 既存不具合と判断する場合は、判断根拠と再現コマンドを最終報告に含める。

#### 担当範囲

- 担当するのはコード変更と動作確認・テストまでとする。
- `git commit`、`git push`、Pull Request作成、tuicr／critによるレビュー、worktreeやブランチの作成・削除は行わない。呼び出し元のClaudeが担当する。
- 指定されたプランファイル自体は変更しない。

#### 最終報告

- 完了またはブロックの状態を明示する。
- 変更したファイルと実装内容を簡潔に列挙する。
- 実行した検証コマンドと、その成否を記載する。
- プランとの差異、置いた仮定、未完了事項があれば明示する。

### ファイル別コーディング規約

コードを作成・変更・レビュー・テストする場合は、作業前に `$coding-rules` Skillを使用する。
Skill内のパス条件に一致する参照をすべて読み、対象ファイルに適用する。

## 環境・ツール

- OS: macOS / Shell: fish
- Python: `uv` を使用（pip/venvの直接操作はしない）
- Node: `pnpm` を使用（npm/yarnは使わない）
- バージョン管理・タスク実行: `mise run`, `task`, `just`
- ファイル閲覧・検索・差分: `bat`, `eza`, `fd`, `sd`, `rg`, `jq`, `yq` を標準ツールより優先してよい
- GitHub操作: `gh` CLI
- Obsidian vault操作: `obsidian` CLI（vault名 `obsidian_notes`）
- プランレビュー: `crit`（`/crit` スキル経由。critセッションがなければ起動する）。
  起動する際は次のどちらで開くかをユーザーに確認してから実行する。
  1. `--no-open` を付け、レビューURLを
     `terminal-browser open <url> --split right` でherdr内のペインに開く。
  2. `--no-open` を付けず、crit標準のブラウザ起動に任せる。
  - `terminal-browser`のリファレンスは `/terminal-browser`で参照できる。
- コード差分レビュー: `tuicr`（`tuicr` スキルのCLI作法をベースに
  `review-local`／`execute-plan-and-pr` スキルで運用）。
  `execute-plan-and-pr` はHerdr環境で `tuicr-wrapper-herdr.sh` により
  ブロッキング起動し、ユーザーが閉じたら自動継続する。
  `review-local` はコメント投稿用セッションを非ブロッキングで開いたままにする。
  非Herdr環境はいずれもユーザーに起動・完了報告を依頼する。
- PRレビュー: `tuicr`（`review-pr` スキル経由）。Herdr環境では右にペインを割いて
  `tuicr pr <PR>` を自動起動し、それ以外はユーザーに起動を依頼する。
  コメント追加後のGitHubへの送信は、ユーザーがTUI内で `:submit` を実行する。

### 破壊的操作の扱い

破壊的な変更を行うコマンドは実行しない。
必要な場合はコマンド内容を提示し、ユーザー自身に `! <command>` で実行してもらう。

- `git push` / `git rebase` / `git reset`
- `rm` / `rmdir` / `rsync --delete`
- `sudo` / `ssh` / `scp`

## コミュニケーションの好み

- 簡潔・直接的な応答を優先する。
- 大きな変更や複数の選択肢がある設計判断は、実装前に方針を確認する。
- 実装プランなど **非コードの成果物** をレビューしてもらう場合は、必ず `/crit` を自動的に実行する。
- コードの差分を変更・実装した後は、tuicrでレビューしてもらう。Herdr環境では自動起動、それ以外はユーザーに起動を依頼してから進める。

## MCP ツールの使い分け（Serena / Graft）

### 基本方針

- **理解・オリエンテーションフェーズ → Graft**
- **編集・リファクタリングフェーズ → Serena**

### Graft を使う場面

- 未知のディレクトリ/機能に着手する最初の一手（`graft_repo_map` で全体像を掴む）
- 「〇〇はどこで実装されているか」を探すとき（`graft_find_code`）
- ファイルを編集する前に影響範囲を確認するとき（`graft_trace_calls` でblast radius確認）
- ファイルの公開APIだけ知りたいとき（`graft_file_api`）
- → **Graftは読み取り専用。コードは変更しない。**

### Serena を使う場面

- 実際にシンボル（関数・クラス・メソッド）を追加・変更・削除するとき
- 特定シンボルの全参照箇所を正確に洗い出してからリネーム/変更するとき（`find_referencing_symbols`）
- 複数ファイルにまたがる一貫した修正（型定義の変更に伴う呼び出し側の更新など）
- セッションを跨いで残しておきたいプロジェクト固有の知見がある場合（Serenaのmemory機能）

### 順序の例

1. `graft_find_code` / `graft_repo_map` で該当箇所と全体構造を把握
2. 変更対象のシンボルが決まったら `graft_trace_calls` で影響範囲を確認
3. Serenaの `find_symbol` で正確な位置を特定 → `replace_symbol_body` 等で編集
4. 編集後、必要なら再度Graftで整合性・影響範囲を確認

### 注意

- 両者は探索機能が一部重複する（grep相当の機能がどちらにもある）。基本はGraftを先に当て、シンボル単位の精密操作が必要になった時だけSerenaのgrep系（`search_for_pattern`など）に切り替える
- Serenaはセッションが長くなると指示を忘れやすい（agent drift）。必要ならSerena公式のhookを`.claude/settings.json`に設定しておく
- Graftは`.claude/skills/graft/SKILL.md`に自分の使い方を書き込むので、CLAUDE.md側は「いつGraftに頼るか」の判断基準だけ書けば十分（ツールの詳細説明はSKILL.md任せでOK）
