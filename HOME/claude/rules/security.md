# セキュリティ

言語・フレームワークを問わず全コードに適用する。認証・ユーザー入力・シークレット・APIエンドポイント・ファイルアップロードを扱う実装では、`security-checklist` スキルの詳細チェックリストも参照する。

## コミット前の必須チェック

- [ ] シークレット（APIキー・パスワード・トークン）をハードコードしていない
- [ ] ユーザー入力をスキーマ（Pydantic / zod）で検証している
- [ ] SQLはパラメータ化クエリ / ORM経由で組み立てている（文字列連結・f-stringで組み立てない）
- [ ] ユーザー由来のHTMLを無害化せずに描画していない（`dangerouslySetInnerHTML` 等）
- [ ] 状態を変更する操作で認証・認可（所有者・ロール）を確認している
- [ ] エラーレスポンス・ログに機密情報（スタックトレース・パスワード・トークン・個人情報）を含めていない

## シークレット管理

シークレットは環境変数（または秘密情報管理サービス）から読み込み、未設定なら起動時に失敗させる。

```python
# BAD
api_key = "sk-proj-xxxxx"

# GOOD: pydantic-settings で必須項目として宣言し、未設定なら起動時に検出する
class Settings(BaseSettings):
    openai_api_key: SecretStr
```

```typescript
// GOOD
const apiKey = process.env.OPENAI_API_KEY
if (!apiKey) {
  throw new Error('OPENAI_API_KEY not configured')
}
```

- `.env` / `.env.local` は `.gitignore` に含め、コミットしない（サンプルは `.env.example` に値なしで置く）。

## 検証した値と使う値を一致させ、信頼境界を意識する

- 検証に使った値（strip 後など）と実際に使う値を一致させる。正規化してから検証し、正規化した後の値を使う。空白・制御文字・非ASCIIがすり抜けないようにする。
- ヘッダーに載せる値（利用者IDなど）は、ヘッダーに載せられる文字だけに絞る。そうしないと、別の層で別のエラーになって現れる。
- リクエスト本文の利用者IDやグループのような値は、呼び出し元の自己申告にすぎない。**何を信頼するか、誰がその値を付けるか**を仕様書に書く。「ヘッダーが空でない」だけで認証済みとみなさない。
- 配列の件数・文字数には上限を付ける。拒否する条件ごとに、その条件だけで拒否されるテストを書く。

## 権限付与（IaC）

- 組み込みロールに含まれる権限は、記憶や推測で判断しない。**公式のロール定義**（Azure なら「Azure built-in roles」の DataActions など）で確かめる。前提が確認できないまま、承認済みの権限構成を変えない。
  - 実例: 「広いロールに書き込み権限が含まれる」と誤認し、承認済みのロール構成を置き換えた。公式定義では含まれていなかった。
- 狭い権限を新設しても、同じ ID に広い権限が付いていれば、制限は効かない。「〜できない」という意図は、その ID に付いている**全ロールの合計**で確認する。
- 上位スコープ（サブスクリプションなど）の設定が、リソース単位の設定を上書きすることがある。
- ロールを追加・変更したら、その権限を説明しているコメント・仕様書・過去の設計判断の記録（「権限の追加は不要」など）が成り立たなくなっていないか確かめる。IaC のテストで、ロール・スコープ・有効化フラグを固定する。

## セキュリティ問題を発見したときの対応

1. 現在の作業を止め、ユーザーに報告する
2. `security-reviewer` エージェントで影響範囲を分析する
3. CRITICALな問題は他の作業より先に修正する
4. シークレットが露出していた場合は、修正とあわせてローテーションが必要な旨をユーザーに伝える（git履歴に残っている可能性も含めて）
5. 同種の問題が他の箇所にないか、コードベース全体をgrepで横展開して確認する（[[design_principles]] の「変更の網羅性の原則」）
